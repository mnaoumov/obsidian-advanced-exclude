# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Obsidian plugin that enhances Obsidian's `Files and links > Excluded files` setting with full `gitignore` syntax. Ignored files become invisible to Obsidian (Files pane, Backlinks, etc.), not just dimmed.

Built on `@mnaoumov/obsidian-lib` with tooling from `@mnaoumov/obsidian-dev-toolkit`, `@mnaoumov/typescript-dev-toolkit` and `@mnaoumov/typescript-test-toolkit`. Patches Obsidian's `FileSystemAdapter` / `CapacitorAdapter` and `FileExplorerView` to filter ignored paths at the source.

## Architecture

- **Root config files** are thin re-exports — actual logic lives in `scripts/`:
  - `eslint.config.mts` → `scripts/eslint-config.ts`
  - `commitlint.config.ts` → `scripts/commitlint-config.ts`
  - `vitest.config.ts` → `scripts/vitest-config.ts`
  - `.markdownlint-cli2.mjs` → `scripts/markdownlint-cli2-config.ts` (via jiti)
  - `.nano-staged.mjs` → `scripts/nano-staged-config.ts` (via jiti)
- **`scripts/`** — all npm script entry points (`jiti scripts/<name>.ts`)
- **`src/`** — plugin source:
  - `main.ts` — Obsidian entry point (default export of `Plugin`)
  - `plugin.ts` — `Plugin` class, wires up child components
  - `ignore-patterns-component.ts` — owns gitignore matching, IndexedDB cache, `.obsidianignore` / `.gitignore` reads. Two tiers of patterns, both always applied in this order: the global ones in the settings (`ignorePatterns`, synced in `data.json`, overlaid by the active profile), then the local ones in `.obsidianignore` (this device only, since Obsidian Sync skips every dot file). The settings tab edits the file through `saveLocalPatterns`, which keeps its line ending and byte order mark (`local-patterns.ts`); a missing file is shown as `LOCAL_PATTERNS_HEADER` and created only by the first edit. A dot file raises no vault event and only the desktop watcher reports it (as `reconcileDeletion`), so `refreshLocalPatterns` re-reads it on window `focus`, on `visibilitychange` to visible, and whenever the tab renders; a change notifies `onLocalPatternsChange`, which re-renders an open tab. A read waits for the save in flight, so its own save is never taken for an outside edit. The verdict fingerprint carries `settingsFingerprint` (effective patterns + scalars) always, so a synced `data.json` re-applies through `applySettingsChange`. A `saveSettings` made while the settings tab is open only raises `hadConfigChanges`, for the tab's hide or Apply to apply; one made while it is closed (a command, another plugin, the demo vault's `configureCommunityPlugin` buttons) runs `processConfigChanges` at once. Guards: `src/settings-save-outside-tab.desktop.integration.test.ts`, `src/local-patterns-tab.desktop.integration.test.ts`
  - `vault-model.ts` — `VaultModel`: the in-memory shadow tree and its bottom-up visibility (`recomputeAll`, `applyDelta`, `seedHidden`)
  - `index-projection-component.ts` — `IndexProjectionComponent`: projects the model onto Obsidian's index in one event-free pass, drives the explorer, owns fast-enable and apply progress
  - `manual-index-hider.ts` — `ManualIndexHider`: S6 direct index mutation — hides/re-inserts files with no events, keeps the in-memory snapshots a same-session un-ignore restores from
  - `vault-path-store.ts` — IndexedDB persistence of the hidden set + universe signature (`IndexedDatabaseVaultPathStore`)
  - `universe-signature.ts` — order-independent signature of the file universe; a mismatch vetoes fast-enable
  - `file-tree-component.ts` — drives Files pane add/delete based on ignore state
  - `data-adapter-safe.ts` — read/write/stat wrappers that survive missing files
  - `indexed-database-utils.ts` — IndexedDB request → promise helper
  - `local-patterns.ts` — text handling of `.obsidianignore`: `normalizeLocalPatterns` (no BOM, LF), `formatLocalPatternsFile` (the file's own line ending and BOM; the platform's line ending for a new file), and the `LOCAL_PATTERNS_HEADER` a new file starts with
  - `pattern-validation.ts` — `validatePatterns`: per-line findings (`error` = the line matches nothing, `warning` = it probably means something else) over a block of pattern text. Each check mirrors what the `ignore` matcher actually does with the line (its bracket scan is a port of `ignore`'s `scanBracket`); nothing reads the vault, since it runs per keystroke. In a profile (`areDirectivesAllowed`) `@` lines are left to `resolveProfile`, which reports the `@import` errors because they need the other profiles
  - `pattern-findings-view.ts` — renders findings (a span in backticks as `<code>`) and `attachPatternValidation`, the debounced live list under the global and local boxes; the profile editor renders the expansion errors and its own findings under "Problems". `IgnorePatternsComponent` raises a `console.warn` + a `Separate` notice (so an apply's progress notice cannot replace it) for an outside `.obsidianignore` edit that brings new errors (seeded silently at load and by the tab's own saves), and for a missing `@import file:` path, remembered per device in `app.saveLocalStorage(REPORTED_MISSING_IMPORTS_LOCAL_STORAGE_KEY)`. Guard: `src/pattern-validation-tab.desktop.integration.test.ts`
  - `constants.ts` — shared constants (`.gitignore` / `.obsidianignore` names, root path)
  - `publish-compatibility-warning-component.ts` — warns when Obsidian Publish is on while `excludeMode === Full`
  - `related-links-batch.ts` — collects Obsidian's per-file `metadataCache.updateRelatedLinks` calls during a bulk re-add and replays them as one `Set`-based pass
  - `folder-listing-suspension.ts` — makes the adapter skip `listRecursive` of the folders a re-show is reconciling chunk by chunk, so their subtree is not created twice, the first time in one burst
  - `file-recovery-suspension.ts` — mutes the core `File recovery` plugin's vault `create` listener during a bulk re-add, so re-shown notes are not snapshotted into IndexedDB
  - `restore-notice-component.ts` — restores hidden files synchronously on unload (added last so it unloads first)
  - `update-progress-notice-component.ts` — progress notice shown while a projection is applied
  - `plugin-settings*.ts` — settings model, component, settings tab. `PluginSettingsComponent.settings` is the base layer the tab edits; every runtime decision reads `effectiveSettings` (base overlaid by the active profile, memoized on the input references, so replace `profiles` with a new array rather than mutating it)
  - `profiles.ts` — profile resolution: `@import <name>` expands linearly, `@reset` clears, `\@` escapes; a profile's own scalars beat its imports; errors skip the line and are reported. `@import file:<vault path>` pastes a vault file's lines literally from the `importedFileContents` map `IgnorePatternsComponent.readImportedFiles` fills (before the fingerprint, and again on the vault `raw` event for an imported path); the file's content reaches the verdict fingerprint through the expanded patterns, so no mtime field is needed
  - `profile-switcher-component.ts`, `profile-suggest-modal.ts`, `profile-edit-modal.ts`, `command-handlers/` — the status-bar switcher, the "Switch profile..." picker, the profile editor, and the two profile commands. The active profile id is per device, in `app.loadLocalStorage('advanced-exclude:active-profile')`; a switch runs `IgnorePatternsComponent.applySettingsChange`, the ordinary config-change path
  - `patches/` — monkey-patches on Obsidian internals:
    - `adapter-patch-component.ts` — dispatches to file-system or capacitor variant
    - `adapter-patch-base-component.ts` — shared `MonkeyAroundComponent` base for both adapter patches
    - `file-system-adapter-patch-component.ts`, `capacitor-adapter-patch-component.ts` — patch `reconcileFile{Creation,Internal}`
    - `vault-load-patch-component.ts` — intercepts initial vault load
    - `file-explorer-view-on-create-patch-component.ts` — patches `FileExplorerView.onCreate`
    - `metadata-cache-initialize-patch-component.ts` — batches the related-links passes of `metadataCache.initialize`'s startup purge
- **Test files** live next to the source: `alpha.ts` → `alpha.test.ts`. Integration tests are named by the vitest project that runs them: `.desktop.` / `.android.` / `.cross-platform.` / `.no-app.` / `.desktop-performance.` / `.demo-vault.` / `.desktop-capture.` / `.android-capture.` + `.integration.test.ts`.
- **`main` field** points to `src/main.ts` (Obsidian plugin source entry — built artifact is `dist/build/main.js`, not published to npm).

## Conventions

- **Mocking**: prefer `strictProxy<T>({...})` / `StrictProxyPartial<T>` from `@mnaoumov/typescript-test-toolkit/strict-proxy` over `as unknown as T` and over `Record<string, unknown>` mock interfaces. Strict proxies throw on uninitialized property access, so mistakes surface in the failing test instead of silently passing.
- **Constructor params**: components take a single `{...}Params` object. When mocking a component constructor in tests, type the params with the real exported `...ConstructorParams` interface — export the interface from the source file if needed.
- **v8 ignore**: only block form (`/* v8 ignore start -- reason. */` … `/* v8 ignore stop */`) is honored. Single-line `/* v8 ignore next */` does not work.
- **Commit messages**: Conventional Commits. Use `npm run commit` (czg) for the interactive wizard.

## Design & History (S6, publish-compatibility, in-memory tree rewrite)

**Publish-compatibility warning shipped.** `src/publish-compatibility-warning-component.ts` (a `LayoutReadyComponent`, wired in `plugin.ts`) warns when Obsidian Publish is enabled while `excludeMode === Full` (the only unsafe combo; `Files Pane` mode is Publish-safe). The warning notice offers four actions: disable `Advanced Exclude`, switch to Files Pane mode, disable the Publish core plugin, or cancel (acknowledge the risk). It revalidates on plugin load (`onLayoutReady`), on `app.internalPlugins` `'change'` (Publish enable/disable), and on settings `saveSettings` (exclude-mode change). The Publish plugin instance implements only `onEnable`/`onDisable` (not `onUserEnable`/`onUserDisable`), so the live hook is the `internalPlugins` `'change'` event, not a `registerMethodPatch` on `onUserEnable` (that would wrap `undefined` and crash). See `docs/sync-and-publish.md` (Publish section).

**S6 (direct index mutation) shipped.** `Full`-mode hide/show no longer calls `reconcileDeletion`/`reconcileFile`. `ManualIndexHider` (`src/manual-index-hider.ts`) removes files from the index directly and fires no events; `IndexProjectionComponent` batches the whole hidden set into one event-free pass and drives the file explorer explicitly. This removes the multi-minute bulk-hide freeze, the synthetic-deletion hazard, and the Obsidian Sync data-loss path. Validated end to end in real Obsidian (`ignore-patterns` + `vault-size-scaling` desktop integration); full unit suite + 100% coverage. See `docs/working-with-other-plugins.md` (S6) and the Known Issues. The show-path `mtime`/`size` staleness check is now implemented (`invalidateStaleSnapshot` + `ManualIndexHider.dropStaleSnapshot`); the one remaining deferred follow-up is a coalesced graph/backlinks refresh. The historical context below predates S6 — read it with that in mind.

Real-vault-scale (~90k) end-to-end testing, via populate-before-open. The harness feature has shipped: `obsidian-integration-testing` 4.3.0 gained `coreSetup({ populate })` + `createSetup({ populate })` so a vault is written with `TemporaryVault.populate()` **before** Obsidian opens it — its startup scan indexes everything in one pass (no `app:reload`, no per-file `adapter.write`). The plugin consumes it via `scripts/vitest-global-setup-performance.ts` (`createSetup({ populate })`) + `scripts/helpers/generate-performance-vault.ts` + a new `integration-tests:desktop-performance` vitest project running `src/vault-real-scale.desktop-performance.integration.test.ts`.

In-memory shadow-tree rewrite. Implemented on branch `feat/in-memory-tree`: `VaultModel` (shadow tree + bottom-up visibility) and `IndexProjectionComponent` replace the whole-vault reconcile walk — initial load snapshots Obsidian's loaded tree and removes only the ignored hide-roots; config changes apply a persistent-model delta; live adapter events sync the model; unload shows a reload notice when paths are hidden. The full known-path set is persisted in IndexedDB (`VaultPathStore`) so a mid-session disable/enable can re-show files whose pattern changed (Obsidian does not re-scan disk then). 200 unit tests, 100% coverage; desktop integration 9/9. Verified live: clean enable ~12 s vs ~80–160 s, zero reconcile walk (persist load ~1 ms, missing-scan ~16 ms — negligible; persists only the hidden set, not all 90k paths).

`IndexProjectionComponent` exposes `isApplyingProjection` (set for the duration of `update()`); the adapter patch's `reconcileDeletion` skips `recordDelete` while it is set (under S6 this is dormant — the projection no longer issues `reconcileDeletion`, so it only guards against a concurrent *real* delete during a projection). `update()` persists the hidden set after each `applyDelta`, so a later reload reconstructs it. Under S6 the same hidden set is also snapshotted in memory by `ManualIndexHider`, so a same-session un-ignore re-shows hidden files instantly from the snapshot (no reload, no re-parse); a path with no snapshot (hidden by a prior session) falls back to `reconcileFile`. That fallback must first `delete adapter.files[path]`: `ManualIndexHider.hide` leaves the adapter's own stat record intact, so without dropping it `reconcileFile` compares disk against the stale record, sees no change, and re-adds nothing (the file would stay hidden forever).

Disable and enable are both fast (issue #10). On disable, `restoreHiddenFilesOnUnload` re-inserts the hidden set from the in-memory `ManualIndexHider` snapshots synchronously in `onunload` (driven by `RestoreNoticeComponent`, added last so it unloads first) — ~9 ms at 90k, no reload notice. On a **warm re-enable** whose ignore config **and** file universe are unchanged, `IndexProjectionComponent.tryFastEnable` seeds the model from the persisted hidden set (`VaultModel.seedHidden`, O(hidden set)) and re-hides it directly — skipping the ~1.4 s 90k cached-verdict `getAll` (now split out of `loadDb` into `IgnorePatternsComponent.loadFingerprint` + a lazy `ensureVerdictsLoaded`) and the whole-vault `rebuild` + `recomputeAll`; the full model build is deferred to the next config change. A change to the vault **while disabled** — which the ignore-file mtime fingerprint cannot see — is caught by an order-independent universe signature (`universe-signature.ts`) persisted alongside the hidden set in `VaultPathStore`: a mismatch (or a changed config, or `FilesPane` mode) falls back to the proven full `applyFull`. Covered live by `src/fast-enable-reenable.desktop-performance.integration.test.ts` on a linked synthetic vault.

**Measured on a copy of a real 115k-file vault, and what that changed.** Obsidian indexes 90,902 nodes of it (dot-folders are never indexed), so the ~90k synthetic vault matches its size. Its shape is deeper: 15k folders. Copy it with text kept and binaries stubbed, then run `lifecycle-scale` against it with `AE_PERF_VAULT_SOURCE` and `AE_PERF_SCENARIO_FOLDER` (see `scripts/vitest-global-setup-performance.ts`). Un-ignoring a 30k-path folder was the slow path, not hiding it. Before → after:

| Step | Before | After |
| --- | --- | --- |
| Same-session re-show | 16.4 s, 118 long tasks | 3.4 s |
| Cross-session re-show (#16, the `reconcileFile` fallback) | ~13–26 files/s, ~20 min | 16 s |
| Warm re-enable | 9 s, two racing whole-vault projections | 0.1 s, fast path |
| Disable | up to 0.9 s | 2 ms |
| App start with the folder hidden | 274 s, the main thread blocked for 268 s | 12.1 s (11.5 s with nothing ignored, 7.1 s with the plugin disabled) |

The worst main-thread task in any step is now ~0.3 s. The causes, each guarded now:

- **The explorer re-sorts the whole vault per change.** `FileExplorerView.onCreate`/`onDelete` call `requestSort`, a 20 ms debounce whose `sort()` re-sorts every folder. The apply loop yields every 50 ms, so it re-sorted a 91k-item tree at every yield. `FileTreeComponent.suspendSort` holds it for the length of an apply and sorts once.
- **Obsidian re-scans every link per created file.** `metadataCache.onCreate` → `updateRelatedLinks([name])` walks every cached file's links, about 30 ms a file. It also matches with `Array.includes`, so passing all the names at once would be worse still. `related-links-batch.ts` collects the names and runs one `Set`-based pass. Both suspensions live in `IndexProjectionComponent.beginBulkIndexUpdate`; nested scopes share the outermost one.
- **`File recovery` snapshotted every re-shown note, and that wedged the next reload.** After layout ready the core plugin listens to vault `create` and, per note, reads its last version from IndexedDB and writes the whole content as a new one. A whole-vault cross-session re-show fired ~93k of these at once, about 186k transactions into `<appId>-backup`, and copied the vault into it. While they drained, every IndexedDB database of the origin timed out on open, so a reload stalled on "Loading plugins..." (`File recovery`'s `onEnable` awaits its database) or "Loading cache..." (the metadata cache), and did not finish within 15 min. With `File recovery` off, the same reload reached layout ready in 9 s. A user's `Reload app` takes the same startup path. `file-recovery-suspension.ts` mutes that one `create` listener inside `beginBulkIndexUpdate`, since a re-shown note is not new content. Edits during the re-show are still snapshotted, through the `modify` listener. Guard: `src/file-recovery-reshow.desktop.integration.test.ts`, red with the suspension removed.
- **Shows ran one awaited round trip per path.** The `stat` of the stale-snapshot check, and the `reconcileFile`, ran one at a time. `showEntries` now runs them in chunks of 200 same-depth paths. Shallowest-first order is kept, so a folder still exists before its files.
- **The first chunk's folder listing re-created the whole subtree in one burst, after an app start.** `reconcileFile` on a folder the adapter has no record of runs `reconcileFolderCreation`, which calls `listRecursive` on the folder's whole subtree, with no bound on concurrency. The show drops each path's record before it reconciles it. In-session, the descendants keep their records, so that listing triggers nothing. After an app start no hidden path has a record, so the first chunk created all ~93k files at once. That held the main thread for ~8 s, as two ~4 s stretches, and the long-task observer caught only one of them. A V8 CPU profile and a Chrome trace show nothing inside either stretch. Then each file's own chunk reconciled it again, so the metadata cache parsed every file twice. `folder-listing-suspension.ts` skips `listRecursive` for the re-shown folders while `showEntries` runs (`Full` mode only), because the chunks cover their subtrees. After a real reload the longest task fell from 4.1-5.3 s to 0.12 s, and metadata parses from 186k to 93k. Guard: `src/folder-reshow-listing.desktop.integration.test.ts`, which drops the descendants' adapter records to reproduce the post-start state. It fails with each file created twice when the skip is removed.
- **An app start with a big folder hidden spent ~10 min before the layout was ready.** At startup `metadataCache.initialize` purges every persisted cache row whose path the vault did not load, and in `Full` mode that is every hidden path. Each purge (`deletePath`) runs `updateRelatedLinks`, which walks every cached file's links, so the purge cost O(hidden × cached). With ~93k synthetic paths hidden, a reload took 634-643 s to settle, with the renderer pegged at one core. `metadata-cache-initialize-patch-component.ts` wraps `initialize` in the same related-links batch as a re-show, and the reload settles in ~5 s. Guard: `src/metadata-cache-initialize.desktop.integration.test.ts`, which restores the hidden paths' cache rows and runs `initialize` again. It counts one related-links pass per hidden path when the patch is removed.
- **Up to three whole-vault projections raced on a mid-session enable.** They came from `onloadAsync`, `IndexProjectionComponent.onLayoutReady` and `IgnorePatternsComponent.onLayoutReady`. An aborted one still rebuilt the shared model, because `rebuildModel` had no abort check after its `await`s. The live projection then read every node at its default `isVisible: false` and **hid the whole vault**. The aborted one also persisted that as the hidden set. Now `rebuildModel` checks the signal and never persists an aborted build. The layout-ready re-projection belongs to the projection alone, and is skipped when the plugin loaded after layout ready.
- **App start is measured by a real reload.** The `restart` step of `lifecycle-scale` reloads the window and polls the new document until the layout is ready, the plugin idle and the metadata queue empty. On the real-vault copy a start with the 30k folder hidden took 274 s before the `metadataCache.initialize` batch above and 12.1 s after it, against 11.5 s with nothing ignored. In `Full` mode the start is followed by the real cross-session re-show. On the synthetic vault a `Full` start settles in ~3.5 s, a `FilesPane` start in ~45-55 s because Obsidian loads all 93k files, and the real re-show takes ~110 s. Those starts run in their own `describe`, first: in the harness-owned instance a reload after the whole lifecycle once never finished starting. After a reload, a connection of the old document keeps a `deleteDatabase` blocked for minutes, so `coldEnable` empties the plugin's stores rather than deleting them. The plugin itself never deletes them.
- **Fast enable now takes an empty persisted hidden set too.** With the config and universe unchanged there is nothing to hide, and it used to rebuild the whole model to find that out.
- **Neither IndexedDB connection was ever closed.** Every enable opened two more, and an open one blocks `deleteDatabase`. Both close on unload now. A connection still opening at unload is closed as soon as it opens, and concurrent `VaultPathStore` loads share one open. Both connections also close on `pagehide`, because a window reload unloads no plugin. That alone did not unblock a `deleteDatabase` straight after a reload in the harness. Queued verdict writes are dropped on unload rather than flushed, since the store is a cache. The debounced flush writes in transactions of 2,000 instead of one ~1 s task, and stops when a store reset makes its verdicts stale.

The regression guard is `src/lifecycle-scale.desktop-performance.integration.test.ts`. It runs each lifecycle step in both modes on the synthetic vault, hiding all of `big`. It bounds wall time per vault path and the longest main-thread task, and asserts that a warm re-enable keeps the vault indexed and takes the fast path. The cross-session re-show of all ~93k synthetic files takes ~105 s. That cost is Obsidian re-reading and re-parsing every file, which is why its ceiling is 3 ms per path.

Scaling is covered at three levels.

`src/vault-size-scaling.desktop.integration.test.ts` (real Obsidian, `Full` mode, end to end): a generic driver that builds a vault, drives the live "edit settings to change ignores" flow (`editAndSave` → `processConfigChanges`), and asserts the event-free hide (zero in-scope `reconcileDeletion`) plus full hide/re-show. Shapes: flat 1000/5000-file folders, a deep+wide nested tree (breadth 4 × depth 4 ≈ 341 folders → one hide-root), and 200 independently-ignored sibling folders (one hide-root each, cost is O(hide-roots) not O(files)). Timeouts are sized from the file count (`60 s + 20 ms × files`).

`src/vault-model-scaling.no-app.integration.test.ts` (no Obsidian, no disk): exercises `VaultModel` directly at 90,000 and 1,000,000 files (single ignored folder → one hide-root) and 10,000 / 100,000 independently-ignored folders. Bench: `recomputeAll` ~40 ms at 100k, ~420 ms at 1M, ~4.5 s at 10M; ~390 MB/million nodes. This proves the **plugin's** hide work is O(N log N) and ~milliseconds at the maintainer's full vault size.

`src/vault-real-scale.desktop-performance.integration.test.ts` (real Obsidian, the `integration-tests:desktop-performance` project, ~90k populated before open): hides the whole vault folder in **`FilesPane` mode** and asserts the explorer is cleared (~0.8 s at 90k). `FilesPane` is used here because it is the fastest mode (pure DOM); since S6, `Full` mode also hides without the freeze, but `FilesPane` remains the cheapest at 90k.

`IndexProjectionComponent.reportApplyProgress` yields on a **time-based** cadence (`APPLY_YIELD_INTERVAL_IN_MILLISECONDS`, reset per `applyDelta`/`applyFull`), not per-N-items. The old per-20-items cadence made the apply loop's wall-clock scale as `itemCount / 20` paint frames — a "hide almost everything" delta (`*` + a few `!whitelist` lines) at 90k spent ~4,500 frames ≈ 72 s **yielding** while the real index work (`recomputeAll` ~70 ms, `ManualIndexHider.hide` ~14 ms) was under 100 ms. This was the true cause of issue #8's "negation is broken" report (the whitelisted content did reappear — it just took ~72 s). Regression guard: `src/vault-hide-timing.desktop-performance.integration.test.ts` asserts the whole op stays under 0.2 ms/path. Note the O(N log N)/~ms scaling claim above is about `VaultModel.recomputeAll`, not the apply loop.

**`FilesPane` mode re-applies onto every explorer that is built after the projection ran (issue #13).** `FileExplorerView.load()` fills `fileItems` from `getAllLoadedFiles()`, so any hide issued before the view existed is lost. At startup the load-time projection runs before Obsidian builds the explorer, so `IndexProjectionComponent.onLayoutReady` calls `reapplyToFilesPane()`. That re-hides the model's hidden set, which `recordCreate` kept current through the vault load. A deferred explorer leaf, revealed later, and a newly opened explorer are both reported by `FileTreeComponent` on `layout-change` and get the same call. `FileExplorerViewOnCreatePatchComponent` likewise retries its prototype patch on `layout-change` when no real view existed at layout ready. Regression guard: `src/files-pane-new-explorer.desktop.integration.test.ts`, which loads the plugin with no explorer present and then opens one. It is red without the fix.

**Settings persistence is guarded by an integration test (issue #14).** `data.json` was emptied and then re-filled with defaults on every reload once a user changed a setting — silent data loss, reported here and, with the same shape, against `CodeScript Toolkit` (#59) and `Embed HTML` (#15). The cause was in `obsidian-dev-utils`, not here: `PluginBase.onload` adds a placeholder `PluginSettingsComponentBase` typed on `Object` before `onloadImpl` installs the real one, and knowing no property names it could only serialize `{}` — which the normalizing save at the end of `loadFromFile` (there to persist migrations) then wrote over the real settings. `obsidian-dev-utils` 94.6.0 skips that save for a component that knows no properties; `advanced-exclude` picked it up in 4.0.0 (`obsidian-dev-utils ^94.6.1`). 3.4.3 — the version #14 was filed against — predates it. `src/settings-persistence.cross-platform.integration.test.ts` is the regression guard: it clears `data.json`, confirms an untouched plugin writes its full default record (since `obsidian-dev-utils` 107.0.0; earlier releases wrote no file), flips `shouldIncludeGitIgnorePatterns`, and re-reads the raw file after each of three plugin reloads. It reloads the plugin rather than the app (the harness has no app-reload primitive) because the placeholder is created on every plugin **enable**, not only at startup — which also explains the "startup resets, disable/enable does not" asymmetry #59 reported: after the first wipe the file is already `{}`, so the next pass has nothing left to erase. Verified both ways — green as shipped, and red (`expected '{}' not to be '{}'`) with that `obsidian-dev-utils` guard neutered in the built bundle.
